# 口播稿人性化处理

本阶段在分镜之前执行。目标是让中文旁白更像真实创作者在说话，同时保留用户原意、事实、数字、产品名称和语气边界。它不是为了规避检测器，也不是为了替用户虚构经历。

## 处理顺序

1. 保存原稿，不直接覆盖用户输入。
2. 把括号内容拆成画面提示；除非用户明确要求，否则不进入旁白和字幕。
3. 扫描 AI 写作痕迹：填充开场、宣传腔、夸大意义、模糊归因、过度连接词、否定式排比、强行三段式、同义词循环、过度限定和空泛结尾。
4. 按口播节奏重写：短句和长句交替，减少书面连接词，优先使用简单的“是”“有”“可以”。
5. 对每个事实、数字、评价和比较保留来源或标记为待验证；不得添加原稿没有的测试经历、用户反馈或第一人称故事。
6. 读稿检查：在正常语速下不能连续出现过长句，产品名、英文缩写和数字要能自然读出。
7. 生成旁白稿、字幕稿和编辑记录，再进入证据映射和分镜。

## 默认改写边界

- 只改表达，不改变结论、立场、事实关系和承诺范围。
- 具体产品名、功能名、命令、路径、URL、API 字段、版本号和数字默认不改。
- 用户提供的个人经历可以保留；模型不得自行添加“我亲自测试过”“用户都在用”等表述。
- 不为了追求“人味”强行添加幽默、第一人称、情绪或跑题内容。
- 技术教程优先清楚、可验证、能听懂；不把免责声明改成肯定语气。
- 付费、能力、兼容性和时效性声明必须标为“需确认”或绑定证据。

## 文案检查表

- 删除“大家好，今天我们来……”等无信息开场，除非它是用户明确要求的固定口播。
- 删除“此外、至关重要、深入探讨、不断演变的格局”等高频套话，除非它们在上下文中确实必要。
- 把“这不仅仅是……而是……”改成直接陈述。
- 三项并列只有在三项本身有叙事价值时保留，否则改成两项或拆成两句。
- 把“行业专家认为、很多人表示、多个报告显示”改成具体来源，或删除未经证实的归因。
- 把“无缝、强大、全面、革命性、令人惊叹”等宣传词换成可观察的功能或限制。
- 删除空泛的“未来值得期待”“迈出重要一步”等结尾，换成明确判断或自然收束。
- 检查破折号、粗体、感叹号和英文副标题是否只是装饰。
- 检查连续三句是否长度和结构相同；至少打断一处节奏。
- 检查每句是否适合大声朗读，字幕是否能切成约 7–14 个汉字一组。

## 输出物

在制作目录保留：

```text
script-original.md
script-revised.md
script-edit-notes.md
```

`script-edit-notes.md` 只记录影响事实、语气、节奏、证据和字幕的修改。建议使用以下记录格式：

| 原文 | 修改后 | 修改原因 | 是否改变事实 | 需要验证 |
|---|---|---|---|---|
|  |  |  | 否 | 否 |

## 旁白、字幕和画面提示的分工

- `script-revised.md`：实际配音文本。
- `storyboard.md` 的字幕列：按最终画面和实际音频切分的字幕，不机械复制整句旁白。
- `storyboard.md` 的画面列：括号提示、证据、动作和素材来源。
- 真实 UI、网页和终端中的原生文字可以保留；作者新增的小字仍受风格和可读性规则约束。

## 质量门槛

交付前确认：

- 大声朗读自然，没有连续的模板化句式。
- 没有虚构个人经验、来源、测试结果或用户反馈。
- 没有因为“人性化”改变用户的核心观点。
- 每个重要结论都能在分镜中找到证据或明确的素材缺口。
- 旁白、字幕和画面提示三者没有混淆。
